# Using Argus

Argus is organized around **projects**. Servers, deployments, monitoring and content attach to projects and environments instead of forcing everything into a customer/account hierarchy.

This guide describes the current operator UI on `main`.

## Global navigation

The left navigation contains the main operational views:

- **Overview** — control-plane summary and recent operational state.
- **Projects** — create and manage project workspaces.
- **Servers** — global managed-server inventory and server details.
- **Jobs** — scheduled/background work and execution state.
- **Notifications** — operational notifications generated by Argus.

A public status page does not use the authenticated control-panel shell.

## Project workflow

A project can be personal, infrastructure-only, experimental, open-source or associated with a client. Client data is optional.

A practical order for setting up a project is:

1. create the project;
2. link one or more GitHub repositories;
3. create environments such as development, staging and production;
4. define services;
5. attach or enroll servers;
6. add Compose stacks and delivery/release information;
7. configure sites and domains;
8. add monitoring and incident automation;
9. use tasks, milestones and notes for project-local work;
10. enable the Content workflow when the project needs structured content or application data.

## Project sections

### Overview

The top of a project shows its status, preset, tags and quick counts for repositories, open tasks, milestones and environments.

### Deploy

The **Deploy** section groups code and delivery concerns.

#### Repositories

Link a GitHub repository by owner and repository name. Argus can then surface synchronized metadata such as:

- default branch;
- visibility;
- open pull requests and issues;
- CI state;
- latest commit;
- last synchronization state/error.

GitHub remains the source of truth. Argus is an operational view over it rather than a replacement for GitHub.

#### Compose stacks

Project Compose stacks can be represented and acted on through the managed infrastructure path. Privileged operations are performed through typed Agent/Helper actions rather than arbitrary remote shell execution.

#### Services

Use the service catalog to describe the runtime pieces that make up the project and associate them with environments and delivery state.

#### Deployments and releases

Track delivery/release records and readiness close to the infrastructure they affect.

### Infrastructure

The **Infrastructure** section contains runtime and hosting configuration.

#### Environments

Create logical environments such as development, staging or production. Servers, services and delivery information can be scoped to the appropriate environment.

#### Add server

To enroll another Linux server:

1. choose the environment;
2. enter the hostname;
3. create a setup code;
4. copy it immediately — it expires after 15 minutes and is intended for one-time use;
5. on the new server run:

```bash
curl -fsSL https://install.noahbozkurt.nl/install | sudo bash
```

6. choose the managed-server/agent install mode and paste the setup code.

See [Installation](installation.md#add-another-managed-server) for the complete host-side flow.

#### Readiness

Use readiness information before treating a deployment/environment as safe to operate or release.

#### Sites and domains

Attach public sites and domains to the project so delivery, monitoring and operational state remain connected to the project rather than living in a separate inventory.

### Observe

The **Observe** section groups monitoring and incident response.

Current project-level capabilities include:

- site monitoring;
- monitor schedules;
- incident automation;
- dependency graph information;
- incidents;
- status pages.

This lets monitoring state and incident context sit next to the services and deployments that caused or are affected by an event.

### Work

The **Work** section is intentionally lightweight and project-local.

#### Tasks

Tasks support status, priority, optional milestone, due date and labels. Use them for work that benefits from staying next to the technical project context.

#### Milestones

Milestones provide delivery checkpoints without turning Argus into a general-purpose issue tracker.

#### Notes

Notes are editable project knowledge for decisions, runbook context or implementation notes that are useful directly inside Argus.

#### Activity

Project activity records recent events and changes for operational context and auditing.

### Content

The **Content** area is the Argus-native entry point into the Payload-backed content platform.

The current foundation includes project-scoped application data and CMS capabilities such as:

- application-data models and records;
- content models;
- drafts and publication;
- version history;
- pages/components and ordered blocks;
- media/image handling;
- project-safe relationships;
- forms and private submissions;
- explicit public reads of published content.

Content is project-scoped so personal/internal projects can use it without requiring a client model.

See [Content Platform](content-platform.md) for implementation and security details.

## Servers

The global **Servers** view is the infrastructure inventory across projects. Managed nodes report through the Argus Agent and use the privileged Helper only for controlled typed host operations.

On a managed host, use:

```bash
argusctl status
argusctl health
argusctl connection
argusctl system info
```

These commands are useful for distinguishing local service problems from authenticated control-plane connectivity problems.

## Jobs

The global **Jobs** view exposes persisted background/scheduled work. Project features such as monitoring rely on the same operational job foundation rather than running only in browser requests.

When debugging a feature that appears not to run, check both its project configuration and the global Jobs view.

## Notifications

The global **Notifications** view is the operator-facing feed for operational notifications. Incident and monitoring workflows can surface relevant events here instead of requiring a separate notification dashboard.

## Status pages

Argus status pages are public-facing views and intentionally bypass the normal authenticated application shell. Configure them from the project Observe section and share the generated public status route as needed.

## Common host commands

Local state:

```bash
argusctl status
argusctl health
argusctl connection
argusctl system info
argusctl version
```

Full installed-system verification:

```bash
sudo argusctl smoke
```

Update:

```bash
sudo argusctl update --version main
```

Rotate the stored GHCR credential:

```bash
sudo argusctl registry-login
```

Uninstall:

```bash
sudo argusctl uninstall
```

For install/update details and current platform limits, see [Installation](installation.md).
