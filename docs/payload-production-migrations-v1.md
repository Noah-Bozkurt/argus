# Payload Production Migrations V1

Payload App Data uses committed migrations in production. Development schema push is never the production deployment mechanism.

## Database ownership

The Rust Control API remains in PostgreSQL's `public` schema. Payload uses the dedicated schema configured by `ARGUS_CONTENT_DB_SCHEMA`, which defaults to `argus_content`.

The initial migration was generated by Payload 3.87 using `payload migrate:create` from the finalized App Data V1 config. Only one manual bootstrap statement was added before Payload's generated SQL:

```sql
CREATE SCHEMA IF NOT EXISTS "argus_content";
```

Payload's generated objects remain schema-qualified. The bootstrap is required because PostgreSQL cannot create schema-qualified enums/tables until the schema itself exists.

## Production startup

`apps/content/src/payload.config.ts` imports the generated migration index and passes it to the PostgreSQL adapter as `prodMigrations`.

With `NODE_ENV=production`, Payload applies pending committed migrations when the content service initializes. `PAYLOAD_DB_PUSH` remains false in production.

## Runtime validation

The initial migration was validated against a clean PostgreSQL 16 database using the same production configuration:

- migration `20260819_073853_initial_app_data` applied successfully;
- 14 Payload tables were created in `argus_content`;
- zero tables were created in `public`;
- the expected workspace/project/model/record/relation tables existed;
- exactly one migration-history row was recorded;
- a second production initialization did not re-run or duplicate the migration;
- the Payload/Next production application build completed successfully from the pnpm monorepo after setting Turbopack and output-file tracing roots to the repository root.

## Creating later migrations

After changing Payload collections or fields:

```text
pnpm --filter @argus/content run migrate:create <descriptive_name>
pnpm --filter @argus/content run generate:types
```

Review the generated migration and snapshot, commit both, and validate against a clean or representative PostgreSQL instance before deployment.

Do not edit historical migrations after they have been deployed. Add a new forward migration instead.

## Deployment requirements

Production requires:

- `DATABASE_URL`;
- `ARGUS_CONTENT_DB_SCHEMA=argus_content` (or another deliberately provisioned isolated schema);
- `PAYLOAD_SECRET`;
- `PAYLOAD_PUBLIC_URL`;
- `ARGUS_CONTENT_SYNC_TOKEN`;
- `PAYLOAD_DB_PUSH=false`.

The database user must be allowed to create/use the configured content schema during the initial deployment and to apply subsequent committed migrations.
